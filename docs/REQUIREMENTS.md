# filesync — 需求说明

> 本文只描述**要什么**，不描述**怎么做**。实现方案见 `DESIGN.md`、`INTERACTION.md`、`UI.md`。
> 每条需求都带可验证的验收标准。

---

## 1. 背景与目标

### 1.1 要解决的问题

团队里有一批文件需要从一个人（或一台机器）分发到其他若干台机器上，但：

* 各人的机器上**文件该放哪**是各人自己的事，不统一
* 分发的内容**会持续变化**，需要定时跟进
* 谁该收到什么，需要**由管理员统一规定**，不能谁都能发给谁
* 收到新文件时，接收方需要**自己决定放到本机哪里**，不能自动乱放

本项目重点解决统一分发权限、下游自主选择保存位置、新文件待定认领这三个问题。

### 1.2 一句话目标

> 由超级管理员定义"谁是谁的上游"，上游把自己的文件发布出来并定时同步，
> 下游按自己的配置把上游的文件拉到本机指定位置；
> 上游新增的文件在下游未指定位置前保持**待定**状态。

### 1.3 规模假设

| 项 | 取值 |
|---|---|
| 节点数 | ≤ 20 |
| 数据总量 | GB 级 |
| 单个文件 | < 100 MB |

## 2. 名词约定

| 名词 | 含义 |
|---|---|
| **中心 / hub** | 一个集中的服务，保存节点关系和文件内容 |
| **节点 / agent** | 装了一台机器上的客户端程序，一台机器 = 一个节点 |
| **上游 / 下游** | 由超管定义的、节点之间的数据流方向。上游提供文件，下游获取文件 |
| **发布** | 管理员声明"本机这些文件要同步给下游" |
| **认领** | 下游用户指定"上游的这个（批）文件，落到本机哪个位置" |
| **待定** | 上游有、下游还没指定位置的文件。**目标位置为空，不下载内容** |
| **送达** | 下游成功把某个文件落到本机指定位置 |

---

## 3. 角色

**关键点：角色不是账号属性，而是"在拓扑里的位置"。** 程序自己从关系里推导：

| 关系中的位置 | 承担的职责 | 对应你说的角色 |
|---|---|---|
| 只有下游 | **发布方**：扫描本机文件并同步出去 | 管理员 |
| 只有上游 | **订阅方**：从上游拉取文件 | 普通用户 |
| 上下游都有 | **禁止**：只允许上游 → 下游两层结构 | 不支持中转 |
| 都没有 | 空转，界面提示"尚未被接入任何关系" | — |

| 角色 | 能做什么 |
|---|---|
| **超级管理员** | 定义节点之间的上下游关系、管理节点与用户。**不参与文件传输** |
| **管理员** | 在自己机器上指定要发布的文件；查看发布内容被下游收到的状态 |
| **普通用户** | 从上游拉取文件；指定本机目标位置；处理待定队列 |

## 4. 功能需求

### FR-1 拓扑管理（超级管理员）

可以定义谁是上游、谁是下游。

| 编号 | 需求 | 验收标准 |
|---|---|---|
| FR-1.1 | 注册节点 | 一台新机器能通过一次性凭证注册到中心，出现在节点列表里 |
| FR-1.2 | 建立上下游关系 | 能指定"A 是 B 的上游"；B 下次拉取关系时能感知 |
| FR-1.3 | 删除关系 | 删边后，下游不再能看到该上游的文件 |
| FR-1.4 | 只允许两层结构 | 禁止自连；有上游的节点不能再有下游，有下游的节点不能再有上游；违反时明确拒绝 |
| FR-1.5 | 查看节点状态 | 能看到每个节点在线/离线/最后活跃时间 |
| FR-1.6 | 下游可见内容一致 | 同一个上游向所有直接下游提供相同的完整发布清单，各下游自行认领 |

### FR-2 角色自动推导

| 编号 | 需求 | 验收标准 |
|---|---|---|
| FR-2.1 | 节点无需配置角色 | 节点上不存在"我是管理员/用户"这样的配置项 |
| FR-2.2 | 从关系推导职责 | 超管建好 A→B 的边后，A 自动承担发布职责、B 自动承担订阅职责，**无需配置角色**；A 仍需选择发布内容，B 未认领的文件仍不下载 |

### FR-3 发布配置（管理员）

管理员指定本机某个目录中的文件（可以多选）作为要同步的内容。

| 编号 | 需求 | 验收标准 |
|---|---|---|
| FR-3.1 | 浏览本机文件系统并多选 | 在界面上浏览目录、勾选文件/目录，不需要手打路径 |
| FR-3.2 | 支持通配过滤 | 可以对选中的目录附加包含/排除规则（如 `**/*.pdf`、排除 `~$*`） |
| FR-3.3 | 发布前预览 | 确认前能看到"将发布 N 个文件 / 共 X MB / 其中 M 个内容未变" |
| FR-3.4 | 事后可改 | 已配置的发布内容可以增加、移除、临时停用 |

### FR-4 定时同步到下游

| 编号 | 需求 | 验收标准 |
|---|---|---|
| FR-4.1 | 定时扫描 | 按固定间隔扫描已配置的目录；间隔可配置 |
| FR-4.2 | 有变化才传输 | 内容没变的文件不重复传输 |
| FR-4.3 | 不做实时监听 | **不使用文件系统实时监听**，只做定时扫描（性能与实现复杂度考虑） |
| FR-4.4 | 上游源文件被删除 | 下游的清单中该文件消失；**下游本机已有文件不做任何删除** |

### FR-5 拉取与落地（普通用户）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| FR-5.1 | 定时拉取上游清单 | 按间隔从上游获取"它当前发布了哪些文件" |
| FR-5.2 | 配置映射规则 | 能表达"上游的 `报价单/` 目录 → 本机的 `~/work/`"这类规则 |
| FR-5.3 | 内容变化自动重同步 | 上游某个文件内容变了，下游**不需要重新指定位置**，直接更新到原位置 |
| FR-5.4 | 上游删除不传播 | 上游删掉文件，下游本机文件**保持不动**，仅在界面上标记为"已失效" |
| FR-5.5 | 目标位置已有同名文件 | 同一来源更新时先备份原文件再原子替换；不同来源争用同一目标路径时拒绝写入并提示冲突 |
| FR-5.6 | 下游备份数量 | 每个文件保留最近 **3 份**备份，新文件成功落地后清理多出的最早备份 |
| FR-5.7 | 离线恢复只收最新 | 下游离线期间上游修改多次，下游恢复后只获取当前最新版本，不补中间版本 |
| FR-5.8 | 多来源目标冲突 | 不同上游的文件映射到同一个本机文件路径时提示冲突，由下游修改位置，不互相覆盖 |

### FR-6 待定队列 ★ 核心

上游新增的文件，下游没有指定本机目标位置的，进入待定。

| 编号 | 需求 | 验收标准 |
|---|---|---|
| FR-6.1 | 自动登记 | 上游新增文件时，下游**自动**产生一条待定记录，**目标位置为空** |
| FR-6.2 | 不下载、不占位 | 未认领的文件**不下载任何内容**，也**不在本机创建空占位文件** |
| FR-6.3 | 逐条认领 | 用户可以为单个文件指定本机目标位置 |
| FR-6.4 | **批量认领** | 用户可以为"某个上游前缀"指定一个本机目录，一次性解决该前缀下所有待定项，**且以后同前缀的新文件不再进入待定** |
| FR-6.5 | 忽略 | 可以忽略某个文件；被忽略的文件以后不再提示 |
| FR-6.6 | 认领即同步 | 认领后立即开始下载并落到指定位置 |
| FR-6.7 | 新增项要显眼 | 新增的待定项有高亮标记，顶部显示"新增 N 个"，可一键跳到下一条 |
| FR-6.8 | 列表稳定 | 出现新文件时，列表不能整屏跳动导致用户正在操作的行跑掉 |

> FR-6.4 是产品能否被接受的关键。没有它，上游每加一个文件用户都要手点一次，
> 待定队列会变成负担。

### FR-7 配置文件可直接编辑

| 编号 | 需求 | 验收标准 |
|---|---|---|
| FR-7.1 | 配置是纯文本文件 | 用任意编辑器直接修改即可，不依赖任何配置界面 |
| FR-7.2 | 改完自动生效 | 保存后**不需要重启程序**，很快生效 |
| FR-7.3 | 工具不修改该文件 | 程序**永远不写入**这个配置文件，避免与用户编辑冲突 |
| FR-7.4 | 写错不致命 | 语法错误时**不应用**、继续沿用上一份有效配置，并提示错误在第几行 |
| FR-7.5 | 配置量可控 | 上游有 500 个文件时，配置文件仍然应该是人能阅读和维护的规模 |

### FR-8 分发状态（管理员）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| FR-8.1 | 看到送达情况 | 能按"文件 × 下游"看到哪些下游已经收到 |
| FR-8.2 | 看出问题 | 能区分"还没轮到""从未收到""下游离线" |
| FR-8.3 | 汇总 | 能看到"B 收到 12/12，C 收到 8/12"这样的汇总 |

### FR-9 失败与重要事件通知

| 编号 | 需求 | 验收标准 |
|---|---|---|
| FR-9.1 | 需要行动的事要提示 | 同步失败、上游长时间离线、待定积压、中心不可达 → 弹出系统通知 |
| FR-9.2 | 不需要行动的不打扰 | 重试后成功、网络抖动自愈 → 只记日志/界面，不弹通知 |
| FR-9.3 | 不重复轰炸 | 同一个问题在冷却时间内只提示一次 |

### FR-10 中心存储的生命周期

| 编号 | 需求 | 验收标准 |
|---|---|---|
| FR-10.1 | 磁盘占用可回收 | 中心不会只涨不跌 |
| FR-10.2 | **中心保留最近两版** | 每个上游的每个发布路径保留最新有效版本及上一个不同内容版本；更早内容不因下游未认领或离线而永久保留；不得清理仍被其他路径当前/上一版引用或正在提交、下载的内容；重复发布相同内容不占用新的版本名额 |
| FR-10.3 | 可审计 | 每次清理删了什么、释放多少，可查 |
| FR-10.4 | 不依赖送达清理旧版本 | 下游一直未接收也不阻止旧版本回收；正在进行的传输结束或安全取消后再释放相关内容 |

### FR-11 界面与交互

| 编号 | 需求 | 验收标准 |
|---|---|---|
| FR-11.1 | 中心 Web 管理 + 节点桌面界面，保留 TUI/CLI | 中心通过浏览器管理节点、关系和接收结果；各节点通过桌面窗口发布、认领和查看状态；桌面支持 Windows/macOS/Linux |
| FR-11.2 | 全键盘操作 | 所有功能都可以只用键盘完成 |
| FR-11.3 | 破坏性操作二次确认 | 首次认领时明确后续自动更新与最近 3 份备份策略；手动清理、删边等操作必须确认，已授权的自动更新不逐次确认 |
| FR-11.4 | 中英文 | 界面语言可切换 |
| FR-11.5 | **界面开关不影响后台** | 关掉界面后同步照常进行；重新打开能看到最新状态 |
| FR-11.6 | 可用脚本调用 | 提供非交互的输出模式，供脚本/CI 使用 |
| FR-11.7 | 系统文件选择器与托盘 | 桌面端通过系统窗口选择发布文件和接收目录；关闭窗口隐藏到托盘，后台继续同步，可从托盘重新打开 |

## 5. 非功能需求

| 编号 | 需求 | 验收标准 |
|---|---|---|
| **NFR-1** | 跨平台 | macOS / Windows / Linux 三平台均可运行；后台为独立可执行文件，桌面安装包携带后台程序，用户无需安装 Rust、Node.js 或 Python；桌面使用系统 WebView，Windows 安装器处理 WebView2 依赖 |
| **NFR-2** | **内存** | 仅每台机器的 **agent 后台进程 < 20 MB**，空闲及同步峰值均需满足；桌面界面及 WebView、TUI、hub 单独计算；以三平台实际进程内存测量验收，不能用语言估算代替 |
| **NFR-3** | 性能开销低 | 稳态（无文件变化）下 CPU 占用接近 0、网络流量接近 0；不因为后台运行影响用户正常使用 |
| **NFR-4** | 大目录友好 | 扫描上万个文件时不应出现明显内存增长（内存占用与文件数量无关） |
| **NFR-5** | 传输可靠 | 传输中断可续传；写入采用"先写临时文件再原子替换"，不产生半截文件；失败可重试 |
| **NFR-6** | 完整性 | 内容落地前后校验哈希，不产生损坏文件 |
| **NFR-7** | 安全 | 下游只能获取自己上游的文件；写入位置严格限制在用户指定的目录内（防路径穿越） |
| **NFR-8** | 后台常驻 | 可注册为系统服务，开机自启，崩溃后能恢复 |

## 6. 明确不做（范围外）

| 不做 | 原因 |
|---|---|
| 双向同步 | 只做单向复制，下游是只读副本 |
| 删除传播（镜像删除） | 上游误删会传导到所有下游，风险不可接受 |
| **中心历史版本 / 回滚服务** | 中心保留最新及上一版，但只向下游分发最新版，不提供历史回放/回滚界面；下游独立保留最近 3 份覆盖前备份 |
| 多层转发 | 只允许上游 → 下游两层，下游不再发布 |
| 文件系统实时监听 | 只做定时扫描 |
| 内容分块 / 大文件优化 | 单文件 < 100 MB，整文件传输足够 |
| 多中心 / 高可用 | 规模 < 20 节点，中心单点可接受 |
| 移动端应用 | 本期做中心 Web 与节点桌面，不做手机端 |
| 对接 LDAP / OIDC | 起步用本地账号 |

## 7. 端到端验收场景

以下场景全部跑通，视为需求达成。

### 场景 1：首次部署

1. 在一台机器上启动中心
2. 创建超级管理员账号
3. 在 A、B 两台机器上安装客户端并注册到中心
4. 超管建立"A 是 B 的上游"的关系
5. **A 的界面显示"我是发布方"，B 的界面显示"我是订阅方"，且 A、B 上都没有任何角色配置**

### 场景 2：管理员发布

1. A 在界面上浏览本机目录，多选若干文件
2. 确认前看到"将发布 5 个文件 / 共 12 MB"
3. 确认发布
4. B 在界面上看到待定队列出现 5 条记录，**目标位置为空，本机没有任何文件被创建**

### 场景 3：批量认领

1. B 在待定队列按 `M`，把 `报价单/` 指定到 `~/work/报价单/`
2. 5 个文件全部落到该目录
3. **A 之后往 `报价单/` 里再加新文件，B 不再进入待定，自动落到同一目录**

### 场景 4：内容更新

1. A 修改了已发布文件的内容
2. 下一轮扫描后，B 自动把新内容更新到**原来的位置**，不需要重新认领
3. **安全起见，B 原来的文件被备份，不是静默覆盖**
4. 连续更新 4 次后，B 只有最新文件和最近 3 份备份

### 场景 5：上游删除

1. A 删除了源目录里的某个已发布文件
2. B 的界面上该文件被标记为"已失效"
3. **B 本机的文件保持不动**

### 场景 6：上游离线

1. A 关机
2. B 显示上游离线，但仍可从中心下载 A 已上传的最新内容
3. A 开机并上传新内容后，B 自动更新；不补齐离线期间的中间版本

### 场景 7：分发可见

1. A 打开分发状态界面
2. 能看到每个已发布文件在 B、C、D 上的送达情况
3. 能看出"node-C 缺 4 个""node-D 离线 3 小时"

### 场景 8：内存与性能

1. 仅 agent 后台进程内存在三平台均 < 20 MB，hub 与 TUI 单独统计
2. 触发一次完整同步，**同步过程中的峰值内存同样 < 20 MB**
3. 扫描一个含 20000 个文件的目录，内存不出现明显增长
4. 无文件变化时，放置 1 小时，CPU 占用接近 0、网络流量接近 0

### 场景 9：配置手改

1. 用户直接编辑配置文件，增加一条映射规则
2. 保存后程序在数秒内生效，**无需重启**
3. 再故意写错语法：程序不崩溃、不停止工作，提示错误行号，并继续使用上一份有效配置
